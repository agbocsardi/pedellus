# Wire protocol v2

Normative contract between the PWA (this repository) and the gateway's `app`
channel (`pedellus`). TypeScript shapes are in [v2.ts](./v2.ts); this
file wins where they disagree. Phase 1 implements everything not marked
_(later)_.

v2 = v1 plus **threads**: one main thread and owner-created side threads.
Everything else in v1 is unchanged. App and gateway ship v2 together; the
gateway accepts only `v: 2` (single owner, no mixed fleet).

## Threads

- `main` always exists, cannot be renamed or archived, and is the default
  wherever a `thread` field is omitted.
- Side threads have gateway-assigned ids `t_` + 1–40 chars `[A-Za-z0-9_-]`, a
  title of 1–80 printable characters, and are separate gateway chats (own
  context, own `/new`, turns may run in parallel). A thread created without
  `from` starts empty. A thread created with `from` is a fork of that thread's
  conversation at that message: it starts with exactly the context the source
  had up to and including it, and records it as `origin`. The inherited
  history is agent context only: it is not re-sent as events of the new
  thread (the app shows a "started from" card quoting the origin message from
  its own store instead). Only `user` and `assistant` messages can be fork
  points; a rejected fork replies `bad_request` and creates nothing.
- At most 50 non-archived side threads. Archived threads are read-only: `send`
  and `control` to them reply `bad_request`. Archiving is not deletion.
- Archiving is manual (`thread.archive`) or automatic: the gateway archives a
  side thread after a configured idle period (default 14 days without
  activity, never while a turn runs) with `archivedReason: "idle"`. A
  scheduled delivery into an archived thread restores it first.
- One event log and one cursor per device across all threads; every
  thread-scoped event names its `thread`.

## Transport

- Same origin for app and API, served behind `tailscale serve` (HTTPS).
- Authentication is the `durable_device` cookie (`HttpOnly; Secure;
  SameSite=Strict; Path=/v1; Max-Age=34560000`), set by `POST /v1/pair`. The
  400-day `Max-Age` matters: iOS drops session cookies when a home-screen app
  is closed, which would force re-pairing. Revocation is server-side. Nothing else
  authenticates; Tailscale identity headers are ignored.
- All JSON is UTF-8. Every size limit below is enforced by the gateway; the app
  enforces the same limits before sending.

| Limit | Value |
|---|---|
| WebSocket frame (either direction) | 262 144 bytes |
| `send.text` | 16 000 characters |
| `send.key` / request `id` | 1–64 characters `[A-Za-z0-9_-]` |
| Pairing code | 8 characters, `[A-Z2-9]` minus `I`, `O` (case-insensitive input) |
| Device label | 1–40 characters, printable |
| `hello.agent` | 1–40 printable characters |
| `control.args` | 1 000 characters |
| Archived threads in a `threads` reply | 200, newest activity first |
| Replay batch per `hello` | 500 events (client re-`hello`s with the new cursor for more) |

These bounds are `LIMITS` in [v2.ts](./v2.ts); the gateway imports a generated mirror of it
(`npm run sync:protocol`, checked by `npm run typecheck`) rather than restating them; `Pairing code` there also carries the alphabet.

## Pairing — `POST /v1/pair`

Request `{"code": "ABCD2345", "label": "iPhone"}`. The code comes from
`pedellus app pair` on the host, is single-use and expires after 10
minutes.

- `204` with `Set-Cookie: durable_device=<token>; …` on success.
- `400 {"error":"bad_request"}`, `401 {"error":"invalid_code"}`,
  `429 {"error":"rate_limited"}` (more than 5 failures per minute across all
  clients). No other information in errors.

## Stream — `GET /v1/stream` (WebSocket)

The gateway always completes the upgrade, then closes with a 44xx code when the
cookie is missing, unknown or revoked, so the browser can tell auth failure from
a network failure.

| Close code | Meaning | App reaction |
|---|---|---|
| 4401 | Not paired / revoked | Drop to the pairing screen |
| 4400 | Protocol violation (bad JSON, unknown op, oversize frame) | Reconnect with backoff, log |
| 4426 | Unsupported protocol version | Show "update the app" (reload) |
| 4409 | Same device opened a newer stream | Do not reconnect while hidden |
| 1001/1006/other | Network or restart | Reconnect with backoff (1 s → 30 s, jitter) |

### Frames

Client → gateway, every request:

```json
{"type":"req","id":"r1","op":"<op>", ...fields}
```

Gateway → client, exactly one reply per request:

```json
{"type":"res","id":"r1","ok":true, ...result}
{"type":"res","id":"r1","ok":false,"error":"<code>"}
```

Error codes are fixed: `bad_request`, `too_large`, `unsupported`, `not_ready`,
`internal`. No free text.

Gateway → client, events:

```json
{"type":"event","event":"<name>", ...fields}
```

### Requests

| op | Fields | Result | Notes |
|---|---|---|---|
| `hello` | `v: 2`, `cursor: number \| null` | `v`, `device` (label), `head` (newest durable cursor), `agent` (display name, 1–40 chars, from gateway config `app.agentName`, default "Durable"), `commands: CommandInfo[]` (the slash commands this gateway offers on the app surface, in menu order), `presets: PresetInfo[]` (selectable model presets, config order; empty when the gateway has none), `uploads: boolean` (whether `POST /v1/upload` is available) | Must be the first request; anything else first → close 4400. A later `hello` on the same stream is allowed and replays again from its `cursor` (how the app fetches the next batch). Wrong `v` → close 4426. After the reply the gateway replays durable events with `cursor > hello.cursor` (oldest first, at most 500), then the current `status` of `main` and of every thread whose state is not `idle`, then live events. |
| `send` | `key`, `text`, `thread?`, `attachments?: string[]` (upload ids, see Files) | `duplicate: boolean` | Idempotent by `key` for at least 7 days: a repeated key returns `ok` with `duplicate: true` and admits nothing. `ok` means durably admitted. |
| `ack` | `cursor` | — | Highest durable cursor the app has stored. Never decreases; a lower value is ignored. Drives retention and "offline" push decisions. |
| `control` | `command` (a name from `hello.commands`), `args?` (≤ 1 000 chars, the text after the name), `thread?` | — | Acts on that thread only. A name the gateway did not list → `unsupported`; bad arguments are answered by a usage `notice`. The visible result arrives as a `message` with `role: "notice"` in that thread. `CommandInfo` = `name` (`[a-z][a-z0-9_-]{0,22}`), `args?` (placeholder, e.g. `"[preset]"`), `summary` (one line), `usage` (the `Usage: /name …` line). With `query` (1–80 chars): every thread, archived included, whose title contains it case-insensitively, newest activity first, at most 200. `ThreadInfo` = `id`, `title`, `archived`, `archivedReason?: "manual" \| "idle"`, `origin?: {thread, messageId}`, `createdAt`, `lastAt` (ISO 8601). The app also keeps this list current from `thread` events. |
| `thread.create` | `key`, `title?`, `from?: {thread, messageId}` | `thread` (new id), `duplicate` | Idempotent by `key` like `send`. Missing title → gateway uses "New thread". Over the limit, or `from` naming an unknown thread/message or a message without a committed transcript entry → `bad_request`. With `from`, forks at that message. |
| `thread.rename` | `thread`, `title` | — | Not `main`. |
| `thread.archive` | `thread`, `archived: boolean` | — | Not `main`. `false` restores. Aborts a running turn in that thread first. |
| `ping` | — | — | App sends every 25 s while visible; no reply within 10 s → app closes and reconnects. |
| `push.key` | — | `key` (VAPID public key, base64url, uncompressed P-256 point) | `unsupported` when the gateway has no push configured. The app passes `key` as `applicationServerKey`. |
| `push.subscribe` | `subscription: {endpoint, keys: {p256dh, auth}}` (the browser's `PushSubscription.toJSON()` fields) | — | One subscription per device; a new one replaces the old. `endpoint` is `https:` on port 443, ≤ 2 048 chars, with a dotted public hostname (no userinfo, IP literal, `localhost` or local-only name); `p256dh` ≤ 128 and `auth` ≤ 64 base64url chars. Otherwise `bad_request`; no push configured → `unsupported`. |
| `push.unsubscribe` | — | — | Removes this device's subscription (idempotent). |
| `answer` | `thread`, `question` (id), `option` (`a`–`d`) | `accepted: boolean` | Answers an open owner question with one of its options (see Owner questions). `accepted: false` for an answered, expired, cancelled, unknown or foreign question; nothing is admitted and a fixed `notice` explains why. |
| `history` _(later)_ | | | |
| `react` | `thread?`, `message` (a `message.id` in that thread whose role is `user` or `assistant`), `emoji` (one of `REACTIONS`, or `null` to clear) | — | The owner's reaction on one message (see Reactions). Unknown or `notice` message, or an emoji outside `REACTIONS`, → `bad_request`. Never starts a turn. |
| `tasks` | `thread?` | `tasks: TaskInfo[]` | That thread's background work (see Tasks), newest first, at most `LIMITS.maxListedTasks`. |
| `task.cancel` | `thread?`, `task` (a `TaskInfo.id`) | `outcome: "cancelled" \| "finished" \| "unknown"` | Cancels one worker or removes one scheduled job of that thread. `finished`: it already ended; `unknown`: no such task in this thread. The visible receipt is a `notice` in the thread. |

### Events

Non-durable events are replaced per thread: a `preview` or `status` only
replaces the previous one of the same thread.

Durable events carry `cursor`: a positive integer, strictly increasing per
device, never reused. Delivered at least once; the app de-duplicates by
`cursor`. Non-durable events have no `cursor` and are replaced by the next of
the same kind.

| event | Durable | Fields |
|---|---|---|
| `message` | yes | `cursor`, `thread`, `id` (stable string), `role: "user" \| "assistant" \| "notice"`, `text` (markdown for `assistant`, plain otherwise), `at` (ISO 8601), `key?` (the `send.key` this is, or answers), `part?: {i, n}` (see Long messages), `attachments?: AttachmentInfo[]` (see Files; on the first part only), `steps?: ActivityStep[]`, `omitted?: number` (assistant only, the turn's tool steps; see Activity; first part only) |
| `settled` | yes | `cursor`, `thread`, `key`, `outcome: "answered" \| "failed" \| "aborted"` — the owner message `key` is finished |
| `divider` | yes | `cursor`, `thread`, `at`, `reason: "new"` — a `/new` context boundary |
| `preview` | no | `thread`, `key`, `text` — full answer-so-far markdown for the running turn (not a delta). Cleared by the matching `message`/`settled`. |
| `status` | no | `thread`, `state: "idle" \| "queued" \| "thinking" \| "tool" \| "error"`, `label?` (short, e.g. tool name) |
| `model` | no | `thread`, `preset` (name of the thread's current preset, or `null` when it uses a model outside the presets) — sent for every thread after replay and whenever a thread's selection changes. Change it with `control {command: "model", args: <preset>}`. `PresetInfo` = `name`, `label?` (short display text), `model` (`provider/model` id), `thinking?`. |
| `question` | yes | `cursor`, `thread`, `id` (10 hex), `prompt`, `options: {id, label, description?}[]` (2–4, ids `a`–`d`), `expiresAt` (ISO 8601), `state: "open" \| "answered" \| "expired" \| "cancelled" \| "unknown"`, `answer?` (option id when answered) — the latest event for an `id` replaces earlier ones |
| `reaction` | yes | `cursor`, `thread`, `message` (message id), `by: "owner"`, `emoji` (or `null` when cleared) — the latest event per (`message`, `by`) wins |
| `thread` | yes | `cursor`, `thread` (`ThreadInfo` fields: `id`, `title`, `archived`, `createdAt`, `lastAt`) — created, renamed, archived or restored |
| `activity` | no | `thread`, `key`, `steps: ActivityStep[]`, `omitted?: number` — the running turn's tool steps so far (see Activity); replaced per thread, cleared by `settled` |
| `login` | no | `thread`, `server` (MCP server name), `url` (one-time authorization URL), `expiresAt` — see MCP login; never stored, never replayed |
| `card` _(later)_ | | |

Ordering for one turn: `message{role:"user",key}` (admission echo, so other
devices see it), `status`/`preview` while running, `message{role:"assistant",key}`,
`settled{key}`.

## Files

Available when `hello.uploads` is `true` (the gateway has media storage
configured); otherwise `POST /v1/upload` answers `400 {"error":"unsupported"}`
and the app hides the attach control.

- **Upload — `POST /v1/upload`.** Cookie-authenticated like the stream. Body is
  the raw file bytes (no multipart), `Content-Type` is the file's MIME type,
  `X-Filename` is the original name, percent-encoded UTF-8, 1–120 characters
  after decoding (untrusted metadata, never a path). At most
  `LIMITS.uploadBytes`. Answers `201 {"id":"f_…"}`; `400 bad_request`,
  `400 unsupported`, `401 {"error":"unauthorized"}`, `413 too_large`,
  `429 rate_limited` (more than `LIMITS.uploadsPerMinute` per device). An
  upload is private to the device that made it until a `send` references it;
  unreferenced uploads are discarded after 24 h. Upload ids match
  `LIMITS.uploadIdPattern`.
- **Attach.** `send.attachments` lists up to `LIMITS.maxAttachments` upload ids
  from this device, each used at most once; `text` may then be empty. An
  unknown, foreign, expired or reused id makes the whole `send` `bad_request`
  and admits nothing. A repeated `send.key` stays `duplicate` as usual.
- **Echo.** The admitted user `message` carries `attachments: AttachmentInfo[]`
  in send order. `AttachmentInfo` = `id`, `name` (bounded original name),
  `type` (MIME as announced), `size` (bytes), `kind: "image" | "audio" | "file" | "artifact"`
  (from the announced type only; the bytes are never sniffed; `artifact` only
  for files the agent sent as one, see Agent files and artifacts).
- **Download — `GET /v1/files/<id>`.** Cookie-authenticated; any paired device
  may fetch a file that a durable message references. Served with the stored
  type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`,
  `Cache-Control: private, max-age=31536000, immutable`, and
  `Content-Disposition: inline` for `image/*` (except `image/svg+xml`) and
  `audio/*`, `attachment` otherwise. `404` for anything else.
- **What the agent sees** follows the gateway's existing media handling (as for
  Telegram): images as image content, audio transcribed when transcription is
  configured, other files as a stored workspace file the agent's tools can read.

## Owner questions

The model's `ask_user` tool (gateway ASK_USER.md) can ask the owner up to four
questions in a mapped app thread. Each question arrives as a durable
`question` event with `state: "open"`; every later change (answered, expired,
cancelled by `/new`, unknown delivery outcome) is a new `question` event for
the same `id`.

- The app renders an open question as a card with one button per option
  (label, optional description). Tapping sends `answer`; the gateway claims the
  question and admits the answer as an ordinary follow-up turn in one commit,
  then sends `question` with `state: "answered"`. The app disables the card
  while the request is in flight and never treats a tap as answered before
  that event.
- Typing an ordinary message instead answers the oldest open question in that
  thread with the typed text, as on Telegram; the gateway then sends
  `question` with `state: "answered"` and no `answer` option.
- Expiry is enforced by the gateway, not a timer in the app. The app may show
  "expires in …" from `expiresAt`, and shows a non-open card read-only with its
  final state.

## Tasks

The Tasks view lists a thread's background work, the same set the agent's own
`worker list` / `cron list` show for that conversation; nothing from another
thread or chat. `TaskInfo` = `id`, `kind: "worker" | "cron"`, `title` (bounded
label or schedule summary), `state: "running" | "queued" | "scheduled" |
"done" | "failed" | "cancelled"`, `createdAt`, `nextAt?` (cron: next run),
`lastAt?` (last run or finish), `detail?` (one bounded line, e.g. the last
result's status). The app fetches it when the view opens and after any durable
event in that thread while it is open; there is no task event stream.
Cancelling asks first in the app and is final; it never restarts or edits
anything.

## Activity

Three levels, so a turn's work is visible without noise:

1. **Status** — the existing `status` pill (`thinking`, `tool` with `label` =
   tool name).
2. **Steps** — while a turn runs, non-durable `activity` events list its tool
   steps so far; the final assistant `message` carries the same list as
   `steps`. The app shows a collapsed "Used N tools" line under the answer
   that expands to the list.
3. **Step detail** — tapping a step shows its tool, outcome and duration.

`ActivityStep` = `id` (stable within the turn), `tool` (tool name, ≤ 64
chars), `state: "running" | "done" | "failed"`, `startedAt`, `endedAt?`. At
most `LIMITS.maxActivitySteps` per turn: the gateway keeps the first
`maxActivitySteps - 1` and the latest one, and sets `omitted` (a count) on
the `activity` event and the message when it dropped any. Steps never carry tool
arguments, results, file paths or error text: the transcript is where those
live, and the app channel state must stay free of anything a tool might have
been handed.

## Reactions

The owner can react to a `user` or `assistant` message in a thread with one
emoji from the fixed set `REACTIONS` (v2.ts), or clear it; one reaction per
message. A `notice` is not a target: the gateway refuses it with
`bad_request`, because a notice is the gateway's own text and a reaction note
would otherwise attribute it to the owner. The gateway
stores the reaction as a durable `reaction` event (so every device shows it) and keeps it
as bounded passive context for that thread's next ordinary owner message, as
Telegram does: at most 8 per thread, a later change to the same message
replaces its note, notes older than one hour are dropped, and the note is
consumed in the same commit that admits that message. A reaction never starts
a turn by itself. The app offers reactions from a small button on a message
(no long-press or swipe gestures); the agent reacting back is *later*.

## Agent files and artifacts

The agent can send files into the thread it is answering with the gateway's
model-facing `app` tool (APP.md), the app counterpart of Telegram's `send`:

- `send` takes one existing workspace file and an optional caption; the
  gateway copies it into app file storage and appends a durable assistant
  `message` with that file in `attachments` (text = the caption, may be
  empty). Same `AttachmentInfo` as owner uploads, same `GET /v1/files/<id>`.
- `artifact` takes one workspace `.html`, `.htm` or `.svg` file (at most
  `LIMITS.artifactBytes`) and an optional title, and sends it the same way
  with `kind: "artifact"`. Artifacts are explainers the agent made, not
  documents the owner sent.

The app shows an artifact as a preview card in the chat that opens full
screen. It renders the file only inside an `<iframe sandbox="allow-scripts">`
(never `allow-same-origin`, `allow-top-navigation`, `allow-forms` or
`allow-popups`) loaded from `GET /v1/files/<id>?view=artifact`, which the
gateway serves with `Content-Security-Policy: sandbox allow-scripts;
default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline';
img-src data: blob:; font-src data:; connect-src 'none'; frame-ancestors
'self'`, so agent HTML runs at an opaque origin with no network and can never
reach `/v1`, the cookie or the app. Without `view=artifact` the file always
downloads as an attachment. Sharing is the file download; the app never
injects anything into the frame. Keyboard focus inside the frame belongs to the
artifact's own document, so the app cannot take Escape back from it; the
viewer's Close button is therefore always on screen and always closes it by
pointer or touch.

## MCP login

When the agent starts an MCP OAuth login in an app thread (gateway MCP.md,
"Login delivery"), the one-time authorization URL reaches the owner as a
non-durable `login` event sent only to devices that have a `hello`'d stream
open at that moment; it is never written to the durable event log, never
replayed and never pushed. If no device is connected, delivery fails and the
gateway cancels that login attempt (the agent may start a new one later).
The app shows it as a card in that thread ("Sign in to <server>") with an
Open button that opens the URL in the system browser; the card disappears on
reload, on expiry, or when the login finishes. When the browser cannot reach
the gateway's loopback callback, the owner pastes the callback URL as an
ordinary message in the same thread: the gateway recognizes it before
admission, hands it to the login, stores none of it, and answers with a
fixed `notice` (the same rules as Telegram). The outcome arrives as an
ordinary `notice`.

## Shortcuts — `POST /v1/ask`

For iOS Shortcuts and similar automations that cannot hold the app's cookie.
Off unless the owner creates a shortcut token on the host
(`pedellus app shortcut add --label <name>`, printed once; stored only
as a hash; `app shortcut list` / `app shortcut revoke <label>`). A shortcut
token is not a device: it cannot open the stream, upload, download, pair or
run controls — only this endpoint.

- Request: `Authorization: Bearer <token>`, JSON
  `{"text": "...", "thread"?: "<id>", "key"?: "<send key>"}` (text and key
  bounded like `send`; thread defaults to `main`, must be open).
- The gateway admits it exactly like an owner `send` from a device (same
  idempotency by `key`; a missing key gets a fresh one), so every app device
  sees the message and the answer in the thread.
- It waits up to `LIMITS.askWaitMs` for that turn to settle: `200
  {"outcome": "answered", "text": "<final answer text>"}` or `200 {"outcome":
  "failed" | "aborted"}`; still running → `202 {"outcome": "pending", "key"}`
  (the answer arrives in the app as usual).
- Errors: `401 {"error":"unauthorized"}` (missing, unknown or revoked token),
  `400 bad_request`, `413 too_large`, `429 rate_limited` (more than
  `LIMITS.asksPerMinute` per token). No other information in errors.
- The token never appears in the event log, channel state, journal or logs.

## Long messages

A message whose `message` frame would exceed the frame limit is sent as `n`
durable `message` events with the same `id`, `thread`, `role`, `at` and `key`,
each with its own `cursor` and `part: {i, n}` (`i` from 0, `n` ≥ 2, at most
`LIMITS.maxMessageParts`). Joining every part's `text` in `i` order gives the
original text exactly; the gateway never splits a UTF-16 surrogate pair and
keeps every part's whole frame within the frame limit. A message that fits has
no `part`. The app stores parts as they arrive and shows the message once all
`n` are present (a partial message shows what it has, marked incomplete).
`settled` for that `key` follows the last part.

## Notifications (Web Push)

Optional; off unless the gateway config has push set up (VAPID keys created by
an explicit owner command; the private key is referenced by env var name and
never leaves the gateway).

- The app asks for notification permission only from a button tap, then calls
  `push.key`, subscribes with `userVisibleOnly: true`, and sends `push.subscribe`.
- The gateway sends a push to a device when a durable `message` with role
  `assistant` or `notice` is appended (first part only for a split message)
  and that device has no open, `hello`'d stream. A device that is connected
  gets no push.
- Payload is content-free JSON, never message text:
  `{"v":2,"thread":"<id>","unread":<n>}` — `unread` is the device's count of
  durable `assistant`/`notice` messages above its acked cursor, capped at 99.
  The `Topic` header is derived from the thread id so a newer push for the same
  thread replaces an undelivered older one; TTL 24 h; urgency `normal`.
- The service worker shows a notification titled with the agent name
  (`hello.agent`, cached) and body "New message" (or "New message in
  <cached thread title>" when the app has it), sets the app badge to `unread`,
  and on tap focuses or opens the app at that thread.
- The app clears the badge when it is visible and has acked everything.
- A push endpoint answering 404 or 410 removes that subscription. Other
  failures are not retried; the next message tries again. Sends are bounded
  (timeout, at most one in flight per device).


| State | Meaning |
|---|---|
| queued | In IndexedDB, not yet sent (offline or not connected) |
| sent | `send` written to the socket, no reply yet |
| admitted | `send` replied `ok` (or the user echo with that `key` arrived) |
| answered / failed / aborted | `settled` arrived |

On reconnect the app resends every queued/sent message with its original `key`.

## App navigation (non-normative)

No swipe navigation: edge swipes collide with browser back gestures in Safari
and installed web apps. The thread list opens from an explicit header control
as a sheet; the main thread is pinned on top. Unread state per thread is local
to the app (last viewed cursor per thread).

Archived ("settled") threads stay findable: the sheet has a search field that
matches thread titles through `threads {query}` and message text through the
app's local store. Message-text search covers what the device has cached.
Manual archive and restore live in the thread's menu. Side threads started
with `from` show a small link chip under their origin message in the source
thread; a side thread's header has an explicit "‹ Main" button.
